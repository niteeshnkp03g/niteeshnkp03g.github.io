New Relic Error Rate Alerting

Production-grade error rate monitoring — NRQL alert conditions trigger AWS Lambda via API Gateway to deliver real-time Open & Resolved Slack notifications with full incident lifecycle visibility and IST timestamps.

Before: Services were checked by hand, so issues could be missed and it was unclear how many services a problem touched.

Impact: Slack alerts arrive within 1–5 minutes and show which services are affected. Also used to watch releases and catch anomalies.

New Relic Response-Time Alerting

APM response-time monitoring with GraphQL alert enrichment — Lambda queries New Relic GraphQL API for threshold details and chart visualisation, adds quiet-hours suppression, then delivers enriched Slack notifications for full lifecycle tracking.

Impact: One response-time alert is an early signal for throughput, database, external-service, application-code and container-crash problems, so triage starts in the right layer.

Zero-Throughput Alerting

Detects services that silently stop receiving traffic. A zero-throughput NRQL condition fires a workflow to Lambda, which posts to Slack and enables or disables P1–P4 alert policies on IST time windows through the New Relic GraphQL API.

Before: Release and outage monitoring was done by hand.

Impact: Alerts fire when throughput drops to zero on important services and APIs, cutting manual release and outage monitoring time by about 70–80% (estimate).

Automated DAG Health Notifications

Replaces manual inbox checks of scheduled-job summaries. Apps Script reads DAG summary emails every 15 minutes, parses the HTML status table, classifies each run as success, failure or anomaly, and posts a structured Slack alert.

Before: Someone had to open each summary email and count successful and failed DAGs by hand, which took team effort and allowed human error.

Impact: Success, failure and anomaly alerts post to Slack automatically, removing manual checks and human error and freeing team time.

API-Level Error-Spike Detection

Catches error-rate spikes on individual APIs. Every 5 minutes a Lambda compares the last 60 minutes with the same hour yesterday and last week, and posts a Slack card when the rate is at least 2x both. A RESOLVED card follows when the spike ends.

Before: Each API's error graph had to be checked by hand.

Impact: Spikes on a single API are flagged by comparing against the same hour on earlier days, so normal daily patterns don't raise false alarms.
